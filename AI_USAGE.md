# AI usage

## Tools

- **Claude Code** (VS Code extension): reading the challenge PDF, planning, scaffolding, writing most of the TypeScript, tests and docs, running the dry runs and tests, inspecting extracted frames, and git commits.
- **Gemini** (runtime, not dev tooling): strategy, storyboard and creative QA inside the pipeline.
- **Veo 3.1** (runtime, Vertex AI): video generation.

## What was AI-generated

Roughly 90% of the code and docs were AI-written. Architecture, provider choice, the concept selection criteria, prompt strategy, QA policy and the graphics direction were discussed and decided in conversation, then reviewed by running the offline pipeline, looking at extracted frames, watching the rendered ads and reading the diffs. The marketing content inside the ad (angles, storyboard, captions, CTA) is generated by Gemini at runtime from the brief.

## AI-generated decisions I changed or rejected

- **A second, human-in-the-loop video path for Kling was removed.** The AI built a `manual` provider: it wrote a handoff file with a Kling-specific prompt for each scene, waited for a person to drop the rendered clip into an `inbox/` folder, and resumed from there, plus its own prompt builder and CLI status flow. It worked, but the challenge needs one provider, and it added a second prompt dialect, a special timeout mode and extra job states to maintain for a path I wasn't going to use. I removed it and kept a single, fully automated Gemini + Veo pipeline. The `VideoProvider` interface still shows where another provider would plug in.
- **Creative QA as a gate that auto-regenerates scenes** when the vision model scores them low was rejected. An LLM's opinion inside a paid render loop can burn credits indefinitely, so QA is advisory (`needs_review` + per-scene issues) and a human decides. This proved right in practice: the same footage scored 5.8 on one evaluation and 5.6 on the next.
- **Caption text generated inside the video** by the model was rejected in favour of ffmpeg-rendered overlays and an end card, because video models garble text.
- **A copy rewrite I didn't ask for was reverted.** When I asked to refine "the text and the CTA", the AI started rewriting the ad's captions and CTA wording. I meant the visual design. The wording changes were reverted and only the typography, layout and CTA button were redesigned.

## Problems introduced by AI that were detected and corrected

1. **Lost failure reason on submit errors.** The first version of `generateScenes` incremented the attempt counter and then called `provider.generate()`. If the submit itself failed (e.g. model not available in region), the scene stayed `PENDING` with no `lastError`, so `status` showed nothing useful. The end-to-end test caught it (`expected FAILED, got PENDING`). Fixed by recording the error on the scene before rethrowing.
2. **Left-aligned multi-line captions.** ffmpeg `drawtext` left-aligns multi-line text even with a centred `x`. This was only visible by actually looking at extracted frames (the end-card headline's second line hugged the left). Fixed by rendering one centred layer per line.
3. **A broken automated patch.** An AI-generated shell edit chained a no-op Python heredoc with `||` before the real Node patch, so the patch silently never ran and the "fixed" render was identical. A second attempt then wrote a literal newline into a TypeScript string. Both were caught by checking output frames and the type-checker rather than trusting the "patched" message.
4. **Test runner failing on Windows.** Every suite failed with `Cannot read properties of undefined (reading 'config')`. Root cause: the shell's cwd used a lowercase drive (`d:`) while Node resolved `D:`, loading two copies of vitest. Fixed with `scripts/test.mjs`, which launches vitest from a normalised cwd.
5. **A letterboxed clip that passed QA.** A real Veo 3.1 render came back as a correct 1080×1920 file with black bars baked into the picture. The technical QA, which only checked dimensions, passed it. It was caught by looking at the frames. QA now measures the actual picture area with `cropdetect` and fails on baked-in bars, assembly crops them off, and a test reproduces the case with real ffmpeg output.
